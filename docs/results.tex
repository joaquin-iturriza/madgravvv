\begin{abstract}
Notes on a set of proposed machine-learning improvements to MADGRAV, a blind
gravitational-wave anomaly search \citep{Inguglia2026}. We reimplement the stage-1 and
stage-2 front end, which the upstream release does not distribute, and evaluate every
proposed change at fixed false-alarm rate against time-slide background pushed through
the same selection as the foreground.
\end{abstract}

\section{Scope and constraints}

Five constraints are inherited from the upstream design and are treated as hard: a
single-detector front end, a fixed parameter budget, a self-supervised stage 1, strict
fold discipline, and no dependence on \texttt{ml4gw}. They are stated in full in
\texttt{CLAUDE.md} and motivated in \texttt{docs/improvement-plan.md}.

The parameter budget is enforced against measured counts read from the distributed
checkpoints rather than inferred from the published topology:

\section{Evaluation protocol}

Detection efficiency is quoted at a fixed false-alarm rate, with the sensitive volume
that implies. Background comes from time slides at lags well clear of the 11\,ms
inter-detector light-travel time, scored by the same selection object as the
foreground. Folds are grouped by GPS time; the evaluation fold is opened once, at the
end, and an audit trail records every access.

\section{Baseline reproduction}
\label{sec:repro}

The distributed weights are calibration-locked to the environment they were trained in:
the upstream \texttt{environment.yml} pins \texttt{torch}~1.12.1 with CUDA~11.2 and
states that a different build can shift the GPU forward pass and break the frozen
false-alarm-rate calibration. That build cannot be installed on the GPUs available to
us, since the CUDA~11.2 wheels predate the driver stack on the partition we run on, so
we use \texttt{torch}~2.6.0 built against CUDA~12.4. The upstream instruction for this
case is to match the pinned build as closely as the hardware allows and re-validate the
bundled recovery demonstration before quoting any false-alarm rate. We report that
re-validation here.

Running the bundled 256\,s segment containing GW190521 through the distributed weights
on a Tesla~V100, we recover

with per-detector significances $\sigma_{H_1}=5.54$ and $\sigma_{L_1}=5.35$, and a single
window above the $\sigma_\mathrm{net}>4$ threshold across the 253 windows of the segment.
The agreement is at the precision the reference values are quoted to.

Two caveats bound what this establishes. First, agreement on one loud event constrains
the forward pass in the regime where the signal is strong; a false-alarm rate is a
property of the noise tail, and the demonstration deliberately quotes none, since a
single short segment carries no time-slide livetime. Second, this validates the
\emph{inference} path only. The second half of the reproduction requirement, that a
reimplemented stage-1 and stage-2 training run recover score distributions and
downstream efficiency matching the distributed weights, requires strain beyond the
bundled segment and is not yet addressed.

We also record a portability defect encountered here, since it affects any new user of
the package. The repository commits nine symbolic links under \texttt{search\_mode/}
that point into the author's own scratch storage. On any other machine these dangle,
and \texttt{driver\_streams.py} calls \texttt{os.makedirs} with \texttt{exist\_ok=True}
at import time, which does not suppress \texttt{FileExistsError} when the path exists as
a dangling link rather than a directory. The documented demonstration therefore fails on
a fresh clone, in a way that resembles a local environment fault.

\section{Whitening: which upstream function the weights were built with}
\label{sec:whitening}

The upstream repository contains two whitening implementations, and they are not
equivalent. \texttt{improved/utilities.py::whiten} divides the Fourier transform by
$\sqrt{S(f) + 10^{-40}}$ and is used by \texttt{whiten\_batch} when preparing training
data. The deployed search does something else: \texttt{MassiveEventPipeline.\_whiten}
calls \texttt{whiten\_batch\_gwpy\_o1}, which builds a \textsc{gwpy}
\texttt{TimeSeries} and applies a time-domain FIR whitening filter against the
run-averaged reference ASD with \texttt{fduration}~$=2$~s and a 20~Hz high-pass, then
notches the calibration and mains lines with $Q=40$.

The distinction matters twice over. First, the additive $10^{-40}$ in the former is an
\emph{absolute} floor, while an O3a reference PSD spans $3\times10^{-51}$ to
$7\times10^{-40}$ and sits near $3\times10^{-47}$ at 100~Hz. The epsilon therefore
exceeds the physical PSD by roughly six orders of magnitude across the whole sensitive
band, and the division degenerates into a near-constant rescaling. The search path
instead floors at $10^{-10}$ times the PSD's own median, which touches no in-band bin.
Second, the FIR conditioning corrupts \texttt{fduration}/2~$=1$~s at each edge of the
window, which is precisely why the pipeline whitens 4~s and retains only the central
2~s of context.

We initially ported the former. On real O3a strain the resulting series correlates with
the correctly whitened one at $0.28$, and its band power is inverted: 19\% below 100~Hz
against 3\% for the search path, and 0.5\% between 100 and 500~Hz against 16\%. Every
tile built before this was corrected is therefore a time--frequency map of essentially
unwhitened, low-frequency-dominated strain, and the stage-1 comparison reported in an
earlier version of this note is withdrawn in full; its measured association between
reconstruction error and tile brightness was a property of that red-tilted input, not of
the model. Nothing in Section~\ref{sec:repro} is affected, because the reproduction gate
executes upstream's own code.

Our implementation now agrees with \texttt{\_whiten} to a relative RMS difference of
$4\times10^{-8}$ on the retained 2~s, which is the float32 round-trip of upstream's own
output, and that agreement is asserted by a test that imports the vendored pipeline
rather than reimplementing it.

A third detail was found in passing. \texttt{improved\_pipeline} defines both O1 and O3a
calibration-line lists and an \texttt{infer\_line\_configuration()} that selects
\texttt{"o3a"} for an O3a preparation directory, but \texttt{\_whiten} passes the string
\texttt{"o1"} literally, so the O3a search notches the O1 calibration lines and the O1
L1 dither lines. We match the deployed behaviour by default, since matching the shipped
weights takes precedence over notching the physically appropriate lines, and treat the
O3a list as an ablation.
